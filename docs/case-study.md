## 문제와 프로젝트의 범위

에이전트의 세션이 끝나거나 컨텍스트가 압축되면 이전의 결정·근거·작업 맥락을 다시 전달해야 한다.
mori는 그 정보를 수집·증류·검색해 다음 턴과 세션에 제공하는 로컬 하네스다.
mori-nest는 여러 작업공간이 공유할 이벤트 로그, 접근 권한, 작업공간 생명주기를 위한 서버다.

TypeScript·Node.js를 사용했다. 로컬 메모리 커널은 better-sqlite3, 공유 서버는 node:sqlite를 사용한다.
mori의 모델·에이전트 실행은 pi 패키지 위에 구성했다.
공유 서버의 독립 구현과 로컬 하네스가 하나의 완성된 운영 서비스로 통합됐다는 주장은 하지 않는다.

## 역할과 개발 방식

최성민(shakystar)이 프로젝트 방향과 주요 설계 결정을 담당하고,
자율 코딩 에이전트 플릿이 작업 분해·구현·테스트·리뷰를 수행하는 방식으로 진행했다.
구현량 전체를 직접 수작업 작성한 코드로 표현하지 않는다.
설계 기여는 사람 결정 기록과 그 결정을 반영한 코드·테스트를 연결해 설명한다.

예를 들어 mori-nest #68에는 사람이 검토·확정한
[2026-08-09 설계 결정](https://github.com/shakystar/mori-nest/issues/68#issuecomment-5230585095)이 보존되어 있다.
아래 사례는 그 결정, 실제 구현, 검증 한계를 함께 보여준다.

## 1. 서명 권한을 배포되는 키로 제한하기

**문제.** 전송 서버는 토큰을 검증해야 하지만 작업공간 토큰을 발급하는 권한까지 가지면 안 된다.
패키지나 저장소를 분리해도 Node의 같은 crypto 모듈에 sign과 verify가 함께 있어,
디렉터리 구조만으로 발급 능력을 제한할 수 없다.

**결정.** 제어 평면에는 Ed25519 개인키를, 전송 평면에는 공개키 집합만 배포한다.
코드는 별도 엔트리포인트와 설정 스키마로 이 경계를 드러낸다.
전송 설정에 개인키가 들어오면 시작 단계에서 거부한다.
독립 버저닝·운영 주체가 필요해지기 전에는 패키지 분리를 추가하지 않는다.

**구현·검증.** mori-nest의 `src/control/index.ts`(`parseControlConfig`),
`src/transport/index.ts`(`parseTransportConfig`), `src/transport/token.ts`와
`test/entry-boundary.test.ts`에서 설정·검증 경계를 확인한다.
토큰 발급과 검증의 상호운용은 `test/control-token.test.ts` 및 제어 서버 테스트로 확인한다.

**한계.** import 그래프 검사는 잘못된 의존을 발견하는 장치다.
실제 운영에서 전송 서버에 개인키를 주지 않았다는 증명은 배포 설정을 별도로 확인해야 한다.

## 2. 실패 후 재시도에도 자원과 결과가 함께 남게 하기

**문제.** 로그나 작업공간을 만든 뒤 멱등 응답 저장에 실패하면, 재시도가 동일 자원을 되찾지 못하거나
중복 자원을 만들 수 있다. 자원 스토어와 멱등 스토어가 서로 다른 DB 연결·파일을 소유하면
두 쓰기를 같은 원자적 작업으로 표현하기 어렵다.

**결정·구현.** mori-nest의 제어 평면 연결을 `ControlDatabase`가 소유하고,
로그·작업공간·자격증명·멱등 리포지토리는 같은 연결을 받도록 구성했다.
생성 라우트는 자원 생성과 멱등 완료를 한 트랜잭션으로 묶는다.
해당 경로는 동기 콜백과 동기 전용 리포지토리 연산을 사용해 커밋 중 이벤트 루프의 끼어듦을 피한다.

**검증.** `test/control-db.test.ts`는 리포지토리 간 롤백을,
`test/control-server.test.ts`는 멱등 완료 실패 시 로그·작업공간이 남지 않는 것,
예약 회수 경쟁, 같은 프로세스 내 요청 인터리빙을 확인한다.
전송 로그는 `UNIQUE(log_id, event_id)`와 트랜잭션을 사용하며,
`test/store.test.ts`에 동시 append·강제 종료 후 내구성·스키마 버전 경쟁 검사가 있다.

로컬 메모리 커널에서도 같은 ‘판단 근거와 커밋의 관계’를 다뤘다.
`appendEvents(expectedHead)`는 트랜잭션 안에서 head를 재확인한다.
증류는 별도로 갱신되는 프로젝션의 지연된 상태 대신 이벤트 로그에서 소비 근거를 복원한다.
`compare-and-append-race.test.ts`와 `consolidate-evidence-binding.test.ts`가
같은 근거를 읽은 두 작업의 경쟁 및 증류·재구성 사이의 창을 검증한다.

**한계.** SQLite에서 성립하는 동기 트랜잭션 규율을 PostgreSQL에 그대로 옮길 수는 없다.
PostgreSQL 이관은 구현하지 않았으며, 연결별 트랜잭션과 동시성 보장을 다시 설계해야 하는 후속 과제로 남겼다.

## 3. 기억 효과를 평가할 때 측정 자체를 검증하기

**질문.** 저장한 기억을 주입하면 세션을 넘어 사용자의 선호를 더 잘 유지하는가?

**평가 설계.** memory-off, memory-on, oracle 세 조건을 비교하고,
시나리오별 결정적 채점과 모델 채점, 호출 비용 및 캐시 적중을 기록했다.
oracle은 정답 단서를 제공했을 때 평가가 차이를 구분할 수 있는지 살펴보는 비교 조건이다.

**관측과 진단.** 세 차례의 기존 자료를 분석했을 때 탭 들여쓰기의 ON−OFF 부호는 안정적이지 않았고,
간결한 답변 선호는 세 회차 모두 음수였다.
pnpm 작업 시나리오에서는 모델이 작업 루트 밖의 실제 저장소를 참조한 오염을 발견했다.
8월 29일 회차의 오염 표식을 제외하면 OFF 3건·ON 4건만 남아 효과를 판정하기 부족했다.
이 수치는 특정 모델·시나리오·표본의 결과로 한정한다.

**후속 구현.** 평가 경로의 bash 쓰기를 Linux user/mount namespace로 제한하는 코드와 회귀 검사를 추가했다.
이 쓰기 경계의 도입만으로 읽기 오염까지 없어졌거나, 새 실험에서 성능이 개선됐다고 주장하지 않는다.
이번 종료 정리에서 확인한 캐시 재생은 9개 조합·45 hit·0 miss이며,
평가 하네스의 재생 가능성을 확인한 결과다. 모델 효과를 새로 측정한 결과가 아니다.

**근거.** [변동성·오염 분석](bench/preference-regression-variance-decomposition-2026-08-30.md),
[8월 29일 실험 기록](bench/preference-regression-3arm-2026-08-29-repeats-default.md),
`packages/mori/src/tools/bash-jail.ts`, `packages/mori/src/bench/preference-regression/`.

## 개발 종료 판단

군 복무 중 개인 프로젝트로 개발했다. 모델 API 사용과 반복 평가에 드는 비용, 복무 중 확보할 수 있는 개발 시간, 관련 도구의 등장을 함께 고려해 추가 개발을 종료했다. 구현한 코드와 검증 기록을 보존하며, 신규 기능 개발과 정기 유지보수는 계획하지 않는다.

한 회차의 비용이 작더라도 시나리오 수정·반복 실험·실패 진단·하네스 유지보수에 드는 누적 자원은 별개다.
과거에 특정 실험을 ‘감당 가능한 예산’으로 판단한 기록과 이후의 개발 종료 판단은 각 시점의 기록으로 보존한다.
프로젝트 전체 지출은 확인되지 않았으므로 개별 비용 원장을 총비용처럼 제시하지 않는다.

관련 도구의 구체적인 대체 범위나 우열은 이 기록에서 확정하지 않는다.
완료한 구현과 확인한 검증 범위를 남기고, 남은 실험과 운영 통합을 후속 과제로 구분해 종료한다.
