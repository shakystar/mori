# Actions 청구 감축 경로 산정 — 레버 전수표 · 잡 수/청구 분 보정 · 도달 조합 (#478 조각 6/N)

#478의 목표는 「전속력 한 달에도 3,000분 안에」이고 완료 기준은 **월 추정 청구가 목표의
절반(1,500) 이하**다. 조각 1~5(#480 · #482 · #486/#488 · #493/#495 · #494/#496)가 깎은 것은
합쳐서 47.1(월환산 잡 수 2,400 → 2,352.9)이다. 조각당 ~9이므로 같은 보폭으로는 닿지 않는다.

이 문서는 **다음 한 조각을 고르는 문서가 아니라, 합이 목표를 넘는 레버 집합을 고르는
문서**다. 코드·워크플로는 바꾸지 않는다.

## 0. 기준 창 · 데이터 출처 · 재현 명령

| 항목                  | 값                                                                                                                                                                                                            |
| --------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 기준 창               | **2026-08-01 .. 2026-08-14 (14일)**                                                                                                                                                                           |
| 창을 여기로 자른 이유 | 08-15 13:39 UTC부터 과금정지 run이 섞이고, 이 리포의 `timing` API가 `total_ms`를 채우지 않아(#480) 집계기가 정지 run과 정상 run을 구분하지 못한다 (`docs/actions-billing-reduction-measurement.md` §(a) 각주) |
| 리포 성격             | private (`gh api repos/shakystar/mori --jq .visibility` → `private`) — 즉 Actions 분은 실제로 청구된다                                                                                                        |
| 러너                  | 전부 `ubuntu-latest` (분 배수 1x)                                                                                                                                                                             |
| 기존 산출물           | `docs/actions-billing-reduction-measurement.md` §(a) 원시 실측 · §(f) 네 번째 잡 해명 · §(g)~(i) `paths-ignore` 반사실                                                                                        |

기준선 재현(청구 **잡 수**, 기존 도구 그대로):

```bash
REPO=shakystar/mori bash .github/scripts/billed-usage-report.sh --since 2026-08-01 --until 2026-08-14
```

청구 **분** 추정은 기존 도구가 내지 않는다(그 이유는 §2). 아래 파이프라인이 이 문서의
분 수치 전부를 낸다 — `gh`와 `jq`만 쓰고 새 워크플로 실행을 유발하지 않는다:

```bash
REPO=shakystar/mori

# 1) 창 안의 run 목록 (553건)
gh api --paginate "repos/${REPO}/actions/runs?created=2026-08-01..2026-08-14&per_page=100" \
  | jq -s -r '[.[].workflow_runs[]?] | .[] | [.id, .name, (.event // "unknown"), .head_sha] | @tsv' > runs.tsv
wc -l runs.tsv   # => 553

# 2) run별 잡 목록 (filter=all). 잡의 started_at/completed_at이 청구 분의 근거다.
: > jobs.tsv
while IFS=$'\t' read -r id name event sha; do
  gh api --paginate "repos/${REPO}/actions/runs/${id}/jobs?filter=all&per_page=100" \
    --jq ".jobs[] | [\"${name}\", \"${event}\", .name, .conclusion, .started_at, .completed_at] | @tsv" >> jobs.tsv
done < runs.tsv
wc -l jobs.tsv   # => 1120  (= §(a)의 청구 잡 수 합계와 정확히 일치)

# 3) 워크플로 × 이벤트별 청구 잡 수 · skipped 잡 수 · 청구 분 추정
jq -R -s -r '
  split("\n") | map(select(length>0)) | map(split("\t"))
  | map({wf:.[0], ev:.[1], concl:.[3],
         min: (if ((.[4]|length)>0 and (.[4]!="null") and (.[5]|length)>0 and (.[5]!="null"))
               then (((.[5]|fromdateiso8601) - (.[4]|fromdateiso8601)) as $s
                     | if $s <= 0 then 0 else (($s/60)|ceil) end)
               else 0 end)})
  | group_by(.wf + "|" + .ev)
  | map({wf:.[0].wf, ev:.[0].ev, jobs:length,
         skipped:(map(select(.concl=="skipped"))|length), minutes:(map(.min)|add)})
  | sort_by(-.jobs)
  | (.[] | "\(.wf)\t\(.ev)\t\(.jobs)\t\(.skipped)\t\(.minutes)"),
    "TOTAL\t\t\(map(.jobs)|add)\t\(map(.skipped)|add)\t\(map(.minutes)|add)"
' jobs.tsv
```

**청구 분 추정 방법과 그 한계 (읽고 넘어가야 하는 부분)**

- GitHub은 **잡 하나하나의 실행 시간을 1분 단위로 올림해서** 청구한다. 그래서 청구 분
  ≈ Σ_잡 `ceil((completed_at − started_at) / 60초)`이고, 위 파이프라인이 그 값을 낸다.
- `timing` API의 `billable.<os>.total_ms`·`job_runs[].duration_ms`는 이 리포에서 **전부 0**이라
  (#480 실측, §(f)의 run 31848253299 예시) 쓸 수 없다. 그래서 잡 목록의 타임스탬프를 쓴다.
- 이 값은 **추정**이다. 청구서와 대조하지 못했다 —
  `gh api users/shakystar/settings/billing/actions`는 이 토큰으로 403(`Resource not accessible
by integration`), org 엔드포인트는 404다. 대조는 사람이 GitHub 결제 화면에서만 할 수 있다.
- 큐 대기 시간은 `started_at` 이후가 아니라 이전이므로 포함되지 않는다. 즉 이 추정은
  실제 청구 분에 **가깝되 정확히 같다고 주장하지 않는다**.
- **2단계 루프가 중간에 실패하면 조용히 작은 합계가 나온다.** `billed-usage-report.sh`가
  부분 결과를 명시적으로 표시하는 것과 달리 위 파이프라인에는 그 장치가 없으므로,
  `wc -l jobs.tsv`가 **1120**인지 확인하는 것이 유일한 가드다. 이 값이 다르면 아래 수치를
  쓰지 마라.
- 창 안 553 run 중 **5 run은 잡이 0건**이다(`30784011527`·`30784009078` = Recheck open PRs ×
  push, `30784011520`·`30784009073` = Refresh armed PRs × push, `30784009091` = CI × push —
  잡이 시작되기 전에 취소된 run). 그래서 아래 표의 「실행 수」와 「청구 잡 수」는
  run 단위로 크로스풋되지 않는다. 이 5 run은 두 지표 모두에 0을 기여한다.

## 2. 잡 수 ≠ 청구 분 — 보정과 판정 단위 못박기

### (2-a) skipped 잡은 몇 개인가

창 안(#495 반영 후) **1,098잡 중 251잡이 `conclusion == "skipped"`**이고, 이들의 청구 분은

청구 분이 0인 잡은 251개보다 조금 더 많다 — **277잡**이다. 차이 26잡은 `cancelled`인데
실행 시간이 1분 미만(대부분 0초)이어서 올림해도 0이 되는 잡이다.

### (2-b) 그래서 잡 수는 분을 과대평가하는가 — **아니다, 과소평가한다**

#510 본문은 「실행되지 않은 잡의 청구 분은 0이므로 「청구 잡 수」 지표는 청구 분을
**과대평가**한다」고 적었다. 창 안에서 실제로 세어 보면 **부호가 반대**다:

```
청구 잡 수 1098   vs   청구 분 추정 1278       → 분이 180 더 크다
```

두 힘이 반대 방향으로 작용하고, 뒤쪽이 이긴다. 잡별 청구 분 히스토그램(#495 반영 후)이
그 계산을 그대로 보여준다:

| 잡의 청구 분 |   0 |   1 |   2 |   3 |   5 |   6 |  10 |  16 |
| ------------ | --: | --: | --: | --: | --: | --: | --: | --: |
| 잡 수        | 277 | 467 | 276 |  74 |   1 |   1 |   1 |   1 |

```
분 − 잡 수 = (0분 잡이 깎는 몫)          + (2분 이상 잡이 더하는 몫)
           = −277                        + (276×1 + 74×2 + 1×4 + 1×5 + 1×9 + 1×15)
           = −277 + 457
           = +180                        ✔ (1278 − 1098)
```

이것은 `docs/actions-billing-reduction-measurement.md` §(d)가 이미 적어 둔 「청구 잡 수는
청구 분의 **하한**」과 같은 방향이며, 이 문서가 그 하한과 실제 값의 간격을 처음으로 실측했다.

### (2-c) 진짜 구조 — 청구 분의 40%는 「1분 올림」이다

벽시계 766.2분이 청구 분 1278로 부풀었다. **차이 511.8분(청구 분의 40.0%)이 잡별 1분

### (2-d) 판정 단위 못박기

> **#478의 완료 기준 `≤ 1,500`은 「월 환산 청구 분」으로 판정한다.**
>
> 근거: #478이 정한 예산 3,000은 GitHub Actions의 **분** 한도이고, 완료 기준은 그 절반이다.
> 「청구 잡 수」는 도구가 먼저 낼 수 있었기 때문에 쓰인 대리 지표이며 §(d)가 이미
> 「청구 분의 하한」으로만 규정했다. 이제 분을 셀 수 있으므로 대리 지표는 보조로 내린다.
>
> - **판정 단위(정본): 월 환산 청구 분.** 현재 **2,738.6** — 목표까지 **1,238.6** 남았다.
> - **보조 지표: 월 환산 청구 잡 수.** 현재 **2,352.9** — #510 본문이 적은 격차 852.9는
>   이 보조 단위의 값이며, 정본 단위의 격차는 그보다 **386 더 크다**.
> - 두 단위를 섞어 더하지 않는다. 아래 모든 레버는 두 단위를 **따로** 적는다.

## 3. 레버 전수표

8행을 하나도 빠뜨리지 않는다. 각 레버에 (a) 절감치(14일 · 월환산, 두 단위) · (b) 산출식 ·
(c) 커버리지·안전 리스크 · (d) 되돌리기 비용을 적는다.
**월환산 = 14일 값 / 14 × 30.**

---

### 행 1 — `Recheck open PRs × push` (69실행 / 331잡 / 310분 → 월 709.3잡 / 664.3분)

#### L1a. discover + recheck 매트릭스를 한 잡으로 접고, `report-discovery-failure`를 `report`에 흡수 (3+N잡 → 2잡)

- **(a) 절감**: 14일 **222잡 / 51분** → 월환산 **475.7잡 / 109.3분**
- **(b) 산출식**: 창 안 `Recheck open PRs × push` 69 run 각각에 대해
  「`Select open PRs`의 벽시계 + 그 run의 non-skipped `Recheck PR*` 잡들의 벽시계 합」을
  한 잡으로 보고 1분 올림, 여기에 `Report results on the PRs`가 실제로 돈 run만 1잡 더한 값.
  결과 109잡 / 259분. 현재값 331잡 / 310분과의 차가 222잡 / 51분이다.
  (`report-discovery-failure`는 67잡 전부 0분이므로 잡 수만 줄고 분은 줄지 않는다 — 이
  레버의 51분은 전적으로 «짧은 잡 여러 개 → 긴 잡 하나»의 올림 절감이다.)
- **(c) 리스크**: 검증 대상 PR 집합·판정·보고는 **완전히 동일**하다(커버리지 손실 0). 잃는 것은
  두 가지다 — ㉠ 매트릭스 병렬성: 열린 PR이 15건이던 run이 창 안에 실재하므로(§3 행1 분포)
  최악 벽시계가 ~2분 × 15 = 30분대로 늘어난다. ㉡ **PR 간 러너 격리**: 지금은 PR마다 새
  러너지만 접으면 한 러너에서 순차로 돌아, 앞 PR의 `pnpm install` 훅이나 남은 프로세스가
  뒤 PR의 판정을 오염시킬 수 있다. #112 항목 5의 위협모델(적대적 PR 작성자 없음) 안에서는
  허용 범위지만 **사고성 간섭**은 새로 생기는 실패 모드다.

## 5. 구조를 바꾸는 선택지 — 사람 결정용

「도달 불가」의 다음 수는 네 갈래다. 절감치는 §3의 행 값에서 그대로 오고, 전부 이 리포
바깥(owner 하네스 또는 인프라)의 작업을 짝으로 요구한다.

### S1. `Recheck open PRs`를 Actions 밖 owner 사이클로 이관 (#478 본문 후보 2)

- **절감**: 행 1 + 행 2 전체 = 월환산 **1,369.3잡 / 1,367.1분**.
  → 잔여 **1,371.4분/월**. **이 하나만으로 목표를 넘긴다.**
- **장점**: (i) 목표 도달이 한 수에 끝난다. (ii) owner 사이클은 이미 6시간 주기로 돌며
  이슈·PR 상태를 읽으므로 「열린 PR을 현재 main과 머지해 검증한다」는 일과 성질이 같다.
  (iii) 캡·기아 같은 임시방편이 필요 없다 — 사이클 주기로 자연히 조절된다.
- **단점**: (i) 검증을 러너가 아니라 owner 워커에서 돌리면 **그 워커의 실행 환경이 CI와
  달라진다** — `ci.yml`이 러너 이미지에 의존한다는 것은 이미 문서화돼 있고(`ci.yml:42-49`
  ImageOS/ImageVersion 캐시 키), `bash-jail.test.ts`는 커널 기능(무권한 user namespace)을
  실제로 쓴다(#489·#497). 「main 기준 그린」의 의미가 미묘하게 달라진다.
  (ii) PR에서 온 코드를 owner 워커에서 실행하게 되므로 #112 항목 5의 격리 논거를
  Actions 잡 경계가 아니라 워커 샌드박스로 다시 세워야 한다. **이것이 가장 큰 쟁점이다.**
  (iii) owner 사이클이 멈추면 재검증이 통째로 멈추고, 그 침묵은 CONTRIBUTING.md 기준
  「코멘트 없음 = 통과」로 읽힌다(#112가 막으려던 바로 그 실패 모드).
- **되돌리기**: 높음. 워크플로 삭제 + owner 구현이 짝이므로 양쪽을 되돌려야 한다.

### S2. `Refresh armed PRs`를 Actions 밖으로 (L5c)

- **절감**: 직접분 월 **240.0잡 / 152.1분** + 미측정 2차분(이 워크플로가 유발하는 `synchronize` →
  행 2·3 비용).
- **장점**: 이 워크플로는 PR 코드를 실행하지 않고 API만 호출한다(`refresh-armed-prs.yml:76-78`).
  즉 S1의 최대 쟁점(격리)이 여기엔 없다. 이미 GitHub App 설치 토큰을 쓰므로 owner 사이클에서
  같은 토큰으로 같은 API를 부르면 된다 — **이관 난이도가 S1보다 훨씬 낮다.**
- **단점**: armed PR의 head 갱신이 owner 사이클 주기만큼 늦어져 auto-merge 대기가 길어진다.
- **되돌리기**: 중간.

### S3. `Notify merge`를 Actions 밖으로 (L6a)

- **절감**: 월 **154.3잡 / 154.3분**. 판정 커버리지 영향 0.
- **장점/단점**: §3 행 6. 네 선택지 중 위험이 압도적으로 낮다.

### S4. self-hosted 러너로 이관

- **절감**: self-hosted 러너의 분은 GitHub에 청구되지 않으므로 **청구 분 지표가 0에 수렴**한다
  (이 문서의 판정 단위 자체가 무의미해진다).
- **장점**: 워크플로를 하나도 바꾸지 않고 목표를 만족시킨다. 커버리지·판정력 손실 0.
- **단점**: (i) 비용이 GitHub 청구에서 인프라 비용으로 **이동**할 뿐 사라지지 않는다 —
  #478이 재려던 것이 «전속력 한 달의 CI 비용»이라면 목표가 형해화된다. (ii) `ci.yml`이
  러너 이미지 식별자를 캐시 키에 넣어 이미지 회귀를 잡는 구조인데(`ci.yml:42-60`),
  self-hosted에서는 그 식별자 계약이 성립하지 않아 가드를 다시 설계해야 한다.
  (iii) PR 코드가 자기 인프라에서 돈다 — #112 항목 5의 위협모델을 처음부터 다시 써야 한다.
- **되돌리기**: 낮음(`runs-on` 한 줄) — 단 인프라는 남는다.
- **⇒ #478 비범위(「Actions 외 CI 제공자 검토」)에 인접하지만 같지는 않다. 사람이
  「목표를 청구 분으로 볼 것인가, 총비용으로 볼 것인가」를 먼저 답해야 판단할 수 있다.**

## 6. 착수 순서와 선행 관계

```
                      [사람 결정: §5의 1·2·3]

        ┌─────────────────────┼──────────────────────┐
        │ (결정과 무관)        │ (S1 = 아니오)          │ (S1 = 예)
```

  - **L1b는 L1a를 선행으로 요구한다** — 캡의 절감치는 잡을 접은 뒤의 벽시계 위에서 계산됐다.
  - **L2b는 실측 조각(조각 D)을 선행으로 요구한다** — §행 2 (c).
  - **L1a·L2a는 S1 결정을 선행으로 두는 것이 합리적이다** — S1을 채택하면 축약한 잡 구조가
    통째로 버려진다. 그래서 조각 C를 결정 뒤로 놓았다.
- 나머지(L4a·L5a·L5b·L6a·L7a)는 서로 독립이고 어느 결정에도 걸리지 않는다.
- **조각 A와 B는 지금 바로 자를 수 있다** (합 월 340.7잡 / 255.0분). 목표에는 못 미치지만
  버려질 일이 없는 투자다.
