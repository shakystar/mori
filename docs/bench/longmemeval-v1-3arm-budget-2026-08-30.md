# LongMemEval-v1(#344) 3-arm 예산 재산정 — v2 방법론을 v1 규모로 재적용 (2026-08-30, #344 조각 1/4)

> **판정 기록 · 동결됨 (커밋 `9ff1c36` 시점).** 이 문서는 그 시점의 기록이며 오늘의 코드를
> 보증하지 않는다. **갱신하지 않는다** — 낡으면 새 문서가 대체(supersede)한다. 인용이 코드와
> 어긋나 보이면 이 문서가 아니라 코드를 따른다.

## 배경

2026-08-30 사람 결정(#344, [코멘트](https://github.com/shakystar/mori/issues/344#issuecomment-5466899939))으로
주 벤치가 LongMemEval-V2 → **v1**로 바뀌었다. [`docs/bench/longmemeval-v2-3arm-budget-2026-08-14.md`](longmemeval-v2-3arm-budget-2026-08-14.md)(이하 "v2 예산 문서")는
그대로 보존하고, 이 문서는 **같은 방법론을 v1 규모에 재적용**한다. v2 예산 문서 자신도 판정
기록으로 동결돼 있으므로 그 문서를 고치지 않고 새 문서를 낸다(CONTRIBUTING.md "`docs/`
문서의 시점 규율").

**재실측하지 않는다** — 아래 단가는 전부 v2 예산 문서에서 그대로 인용한다:

- 원장 역산 단가(#401 실측, DeepSeek `deepseek-v4-flash`): input **$0.14/M**, output **$0.28/M**
  (v2 예산 문서 §2).
- 티어별 블렌디드 단가(InMind 앵커, 입력 1M당·출력 15% 내장): DeepSeek V4 Flash
  **$0.1822/M**, GPT-5.6 Luna **$0.3810/M**, Claude Sonnet 4.6 **$5.2607/M** (v2 예산 문서 §3).
- OFF 팔 근사 배율(DeepSeek 실측 input:output 비로 역산): **0.769**(v2 예산 문서 §4-c).

## 1. v1 규모

#344 본문 §배경: `LongMemEval_S`, 문항당 ≈115k tok, 500문항, 총 **≈57.5M tok**. v2(문항 1개
25M~115M)와 달리 v1은 **문항 하나가 아니라 벤치 전체가** 이 규모다 — 그래서 이 문서의 표는
v2 예산 문서처럼 "문항 1개 비용 범위"가 아니라 **"전량 500문항 1회차 비용"**을 낸다.

## 2. arm 구성 — v1은 OFF / mori(ON) / ORACLE 셋뿐이다

#344 본문 §프로토콜: "팔 구성은 기존대로 **ON / OFF / ORACLE 3팔**." v2 예산 문서가 다뤘던
"공식 memory tool(`memory_20250818`)" 팔은 v1 프로토콜에 없다 — 이 문서는 그 팔의 예산을
내지 않는다.

세 팔의 구조적 차이는 `packages/mori/src/bench/preference-regression/runner.ts`(착수 시점
기준)에서 확인했다(재실측이 아니라 코드 구조 확인이다 — 달러 수치는 여전히 위 §의 기존
단가만 쓴다):

- **세 팔 모두 같은 맥락 세션(`contextTurns`)을 돈다** (`runner.ts:473` 주석, #434) — 이 부분의
  토큰 비용은 팔 간에 동일하다.
- **compact() 호출**: `runner.ts:545`가 `condition === "memory-off" || condition === "memory-on"`일
  때만 압축을 부른다 — **OFF와 mori(ON) 둘 다 압축 호출이 있고, ORACLE에는 없다.** (v2 예산
  문서 §4-c는 "OFF만 압축한다"고 적었는데, 그 뒤 #459로 mori 팔에도 폴백용 압축이 추가돼
  현재 코드와 어긋난다 — v2 문서는 동결 기록이라 고치지 않는다.)
- **mori 스토어 사용**: `usesMoriStore = condition === "memory-on"`(`runner.ts:512`) — OFF·ORACLE은
  스토어를 아예 열지 않는다.
- **ORACLE의 맥락 세션은 후속 세션에 영향을 주지 않는다**(`runner.ts:478` 주석) — 이월되는
  것은 정답 라벨뿐이고, 그래도 비용 축 비교 가능성을 위해 세션 자체는 돈다.

즉 **ORACLE은 구조적으로 OFF의 부분집합이다**: 같은 맥락 세션을 돌리되 압축 호출 하나가
빠진다. 이 관계는 §4에서 ORACLE 행의 상한을 정하는 근거로 쓴다.

## 3. 예산 표 — arm × 티어 (전량 57.5M tok, 1회차)

### mori(ON) — v2 예산 문서 §4-a와 동일 산식 (블렌디드 단가 그대로 곱)

| 티어              | 블렌디드 단가 | 전량 패스   | Batch 50% 할인 후 |
| ----------------- | ------------- | ----------- | ----------------- |
| DeepSeek V4 Flash | $0.1822/M     | **$10.48**  | **$5.24**         |
| GPT-5.6 Luna      | $0.3810/M     | **$21.91**  | **$10.95**        |
| Claude Sonnet 4.6 | $5.2607/M     | **$302.49** | **$151.25**       |

### OFF — v2 예산 문서 §4-c와 동일 산식 (블렌디드 단가 × 0.769)

| 티어              | 근사 단가 (블렌디드×0.769) | 전량 패스    | Batch 50% 할인 후 |
| ----------------- | -------------------------- | ------------ | ----------------- |
| DeepSeek V4 Flash | ~$0.1401/M                 | **~$8.06**   | **~$4.03**        |
| GPT-5.6 Luna      | ~$0.2930/M                 | **~$16.85**  | **~$8.42**        |
| Claude Sonnet 4.6 | ~$4.0455/M                 | **~$232.62** | **~$116.31**      |

(`~`는 v2 예산 문서와 같은 이유 — DeepSeek에서만 실측된 input:output 비를 다른 두 티어에
전이했다는 한계가 그대로 상속된다.)

### ORACLE — 상한만 낸다 (OFF 행 그대로, §2의 구조적 부분집합 관계)

| 티어              | 전량 패스 상한 | Batch 50% 할인 후 상한 |
| ----------------- | -------------- | ---------------------- |
| DeepSeek V4 Flash | **≤ $8.06**    | **≤ $4.03**            |
| GPT-5.6 Luna      | **≤ $16.85**   | **≤ $8.42**            |
| Claude Sonnet 4.6 | **≤ $232.62**  | **≤ $116.31**          |

**이 상한은 재추정이 아니라 OFF 행의 재인용이다.** §2에서 확인했듯 ORACLE은 OFF와 같은 맥락
세션을 돌리되 압축 호출 하나가 빠진 구조적 부분집합이므로, ORACLE의 실비용은 OFF보다
낮거나 같다. 압축 호출분을 원장에서 단독으로 분리할 방법이 없다는 한계는 v2 예산 문서
§4-c가 이미 밝힌 것과 같아서(비용 축이 호출별이 아니라 축 단위로만 누적된다), 이 문서에서
새로 추정하지 않고 **상한으로만** 쓴다 — 예산 판정(§4)에는 상한을 쓰는 쪽이 안전하다(실비용을
과소평가할 위험이 없다).

## 4. 판정 — 전량 회차는 세 티어 모두 감당 가능하다, 부분 슬라이스 불필요

**세 팔(OFF/mori/ORACLE) × 세 티어 전량 회차 모두 예산 안에 들어온다.** 가장 비싼 조합인
Claude Sonnet 4.6 × mori(ON)도 Batch 할인 후 **$151.25**(할인 전 $302.49)로 세 자릿수
달러이긴 하지만, v2 예산 문서가 "세 자릿수 달러"를 문제 삼은 맥락은 **나이틀리 반복 실행**
전제였다(v2 예산 문서 "판정 먼저" 절) — v1 베이스라인 회차는 #344 완료 조건상 1회성 확정과
이후 북극성 기능 착지 시 재실행뿐이지 나이틀리가 아니다.

2026-08-10 사람 결정(§3, v2 예산 문서 인용)이 **최저가 티어를 기본값**으로 못 박았으므로
실제 착수 시 기본 선택은 **DeepSeek V4 Flash**다 — 이 티어에서 세 팔 합산 전량 비용은
Batch 할인 후 대략 **$4~5 수준**(mori $5.24 + OFF $4.03 + ORACLE ≤$4.03 ≈ $13.30 안팎, 세 팔을
모두 돌려도)으로 사실상 무시할 수 있는 금액이다.

**부분 슬라이스 권고치는 필요 없다** — 최저가 티어 기준으로도, 상한으로 잡은 최고가 티어
(Claude Sonnet 4.6, mori 팔 $151.25) 기준으로도 예산을 위협하는 규모가 아니다. 다른 티어로
교차검증(§3 각주의 GPT-5.6 Luna, 혹은 상한 확인용 Claude Sonnet 4.6)을 돌리더라도 1회성
지출로는 그대로 감당 가능하다.
