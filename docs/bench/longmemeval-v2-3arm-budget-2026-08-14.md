# LongMemEval-V2(#344) 3-arm 예산 재산정 — #401 실측 기반 (2026-08-14, #343 조각 4/4)

## 판정 먼저

**mori 팔·공식 memory tool 팔은 DeepSeek V4 Flash에서 회당 한 자릿수~두 자릿수 달러,
Claude Sonnet 4.6에서는 회당 세 자릿수 달러다.** 3-arm 전량(25M~115M 토큰 궤적 범위)을
프론티어 티어로 반복 실행하는 것은 나이틀리 케이던스(#397)와 양립하지 않는다 — 최저가
티어가 기본값이어야 한다는 2026-08-10 사람 결정 §3이 이 규모 차이로 다시 확인된다.

이 재산정은 **#401(PR #444)의 실측 usage를 유일한 실측 입력**으로 쓴다. #401의 점수 축은
킬 스위치 발동으로 무효이지만, 비용 축은 에피소드가 실제로 돌았다는 사실만으로 유효하다
(owner 2026-08-14 게이트 해소 코멘트, [issue #402](https://github.com/shakystar/mori/issues/402)).

## 1. #401 3팔 ↔ #344 3-arm 매핑

#344 본문(및 2026-08-10 사람 결정 §2)이 정의하는 3-arm은 **OFF / mori / 공식 memory tool
(`memory_20250818`)**다. #401이 실제로 돌린 3팔은 **memory-off / memory-on / oracle**이다.
두 축은 이름이 겹치지만 셋 중 둘만 대응한다:

| #401 팔 (실측) | #344 arm         | 대응                                                                                                                                                      |
| -------------- | ---------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `memory-off`   | OFF              | 직접 대응 — 하네스 기본 압축 요약만 남기는 베이스라인, 정의가 같다                                                                                        |
| `memory-on`    | mori             | 직접 대응 — mori 증류+retrieval, 본 수치                                                                                                                  |
| `oracle`       | _(없음)_         | **대응 없음.** `impliedPreference` 직접 주입은 #401 자체의 천장 참조용 3번째 팔이지, #344의 공식 memory tool과 다른 목적(경쟁 시스템이 아니라 상한선)이다 |
| _(없음)_       | 공식 memory tool | **#401에서 실측되지 않음.** 미구현(#344 자체 스코프) — 아래 §4는 실측이 아니라 구조적 유추에 의한 **추정치**다                                            |

이슈 본문이 예고한 3-arm(① OFF ② mori ③ 공식 memory tool)과 #401의 3팔이 이름은 같아도
셋째 항이 다른 것을 확인한 것이 이 표다 — 2026-08-10 owner 코멘트가 지적한 매핑 불일치를
여기서 명시적으로 닫는다.

## 2. 기준 단가 산정 — 원장(ledger)을 쓰고, 그 이유

**원장 수치를 기준으로 삼는다.** [#401 run 문서](preference-regression-3arm-run-2026-08-14.md)
§3은 원장 집계($0.0170)와 프로바이더 잔액 실측($0.52)이 30배 갈리는 이유를
"cost-ledger가 캐시 replay 호출도 원래 호출의 `usage.cost`를 그대로 계상하기 때문"으로
규명했다. 이 재산정이 원장을 쓰는 것은 그 결론과 모순되지 않는다 — **원장 "총액"이 아니라
원장에서 역산한 "토큰당 단가"를 쓴다.**

이 구분이 성립하는 이유: 캐시 replay가 총액을 부풀리더라도, 매 replay는 원본 호출의
`(cost, tokens)` 쌍을 통째로 복제한다 — 분자·분모가 같은 배수로 늘어나므로 **`cost ÷ tokens`
비율 자체는 replay 중복에 영향받지 않는다.** 그리고 LMEv2는 매 태스크가 새 프롬프트라
(#340이 지배 항목으로 적은 궤적 ingestion 자체가 반복되지 않는 원본 텍스트다) 캐시 히트를
가정할 수 없다 — 즉 "캐시 없이 다 쳤다면 들었을 단가"가 정확히 이 예산이 원하는 값이고,
원장에서 역산한 단가가 바로 그것이다.

`docs/bench/reports/preference-regression-3arm-2026-08-14.json`의 `total`에서 역산(DeepSeek
`deepseek-v4-flash`, 이번 실측에 쓰인 유일한 모델):

| 항목   | 토큰   | 원장 비용   | 단가(역산)    |
| ------ | ------ | ----------- | ------------- |
| input  | 56,668 | $0.00793352 | **$0.14 / M** |
| output | 25,689 | $0.00719292 | **$0.28 / M** |

## 3. 티어별 블렌디드 단가 — InMind 앵커와의 교차검증

2026-08-10 사람 결정 §4는 InMind 재검토용으로 16.3M 입력 + 15% 증류 출력(2.445M) 가정 아래
3개 티어의 총액을 이미 냈다: DeepSeek V4 Flash $2.97 / GPT-5.6 Luna $6.21 / Claude Sonnet 4.6
$85.75. 이 재산정은 그 총액을 "입력 1M-token당 블렌디드 단가"로 환산해 재사용한다
(`총액 ÷ 16.3`, 15% 출력 가정이 이미 내장된 값):

| 티어              | 총액(InMind, 16.3M+2.445M) | 블렌디드 단가 (입력 1M당, 출력 15% 내장) |
| ----------------- | -------------------------- | ---------------------------------------- |
| DeepSeek V4 Flash | $2.97                      | **$0.1822 / M**                          |
| GPT-5.6 Luna      | $6.21                      | **$0.3810 / M**                          |
| Claude Sonnet 4.6 | $85.75                     | **$5.2607 / M**                          |

**교차검증**: §2에서 실측으로 역산한 DeepSeek 단가(input $0.14/M, output $0.28/M)를 같은
15% 출력 가정에 대입하면 `0.14 + 0.15 × 0.28 = $0.182/M` — 위 표의 $0.1822/M과 사실상 일치한다
(반올림 오차 범위). **InMind 견적에 쓰인 모델링 방법론이 #401의 실측과 독립적으로 같은
숫자를 낸다** — 이 재산정이 그 방법론을 LMEv2로 그대로 옮기는 근거다.

## 4. LMEv2 예산 표 — arm × 티어 (25M~115M 토큰)

#340이 LMEv2의 지배 항목으로 적은 궤적 ingestion 25M~115M 토큰 범위에 §3의 블렌디드 단가를
적용한다. **이 범위는 "한 번의 전량 ingestion 패스" 비용이다** — mori 팔과 공식 memory
tool 팔처럼 궤적 전체를 한 번 읽어 자기 표현(증류물)으로 만드는 arm에 그대로 적용된다.

| arm                         | 티어                                             | 25M 토큰 | 115M 토큰 |
| --------------------------- | ------------------------------------------------ | -------- | --------- |
| **mori**                    | DeepSeek V4 Flash                                | $4.56    | $20.95    |
|                             | GPT-5.6 Luna                                     | $9.52    | $43.81    |
|                             | Claude Sonnet 4.6                                | $131.52  | $604.98   |
| **공식 memory tool** (§4-b) | _(아래 §4-b 참고 — 위 표를 그대로 쓰면 안 된다)_ |          |           |
| **OFF** (§4-c)              | DeepSeek V4 Flash                                | ~$3.50   | ~$16.12   |
|                             | GPT-5.6 Luna                                     | ~$7.33   | ~$33.70   |
|                             | Claude Sonnet 4.6                                | ~$101.17 | ~$465.37  |

(답변·judge 호출은 프로토콜이 `gpt-5-mini`로 고정하며 위 표에 넣지 않는다 — 2026-08-10
사람 결정 §4가 이미 "별도 소액"으로 분리했고, 내부 모델 선택과 무관하다.)

### 4-a. mori 팔 — §3 표 그대로

mori 팔의 ingestion(distillation)은 InMind 견적과 동일한 성격의 작업이다(궤적을 읽어
구조화된 기억으로 압축) — §3의 블렌디드 단가를 그대로 곱한 값이 위 표다.

**다만 이 값 자체가 과소추정일 가능성이 있다 — §5-a 참고.**

### 4-b. 공식 memory tool (`memory_20250818`) 팔 — mori와 같은 산식을 쓰면 안 되는 이유

**이 arm에 §3의 ingestion 단가를 그대로 적용하는 것은 구조적으로 부정확할 가능성이 높다.**
`memory_20250818`은 Anthropic 자체 Memory tool(파일 기반 `/memories` 디렉터리를 모델이
`view`/`create`/`str_replace` 같은 tool call로 직접 읽고 쓰는 방식)이다. mori의 증류처럼
궤적 전체를 별도 LLM 패스로 재처리해 압축본을 만드는 구조가 **아니다** — 메모리 읽기/쓰기가
**주 답변 모델 자신의 turn 안에 tool call로 얹힌다.** 즉 "궤적 25M~115M 토큰을 한 번 더
통째로 읽는 별도 ingestion 패스"라는 전제 자체가 이 arm에는 성립하지 않을 수 있다.

구조적으로 더 가까운 쪽은 mori 행이 아니라 **OFF 행**이다 — 별도 재처리 패스 없이 주 대화
토큰에 증분 비용이 얹힌다는 점이 같다. 하지만 이것도 유추이지 실측이 아니다: 파일 기반
메모리는 세션이 길어질수록 메모리 파일 자체가 반복 재노출(view)되어 mori에 없는 자기만의
비용 패턴을 가질 수 있다.

**결론: 이 arm은 이번 재산정에서 달러 수치를 내지 않는다.** #344가 실제로 이 arm을 구현하기
전까지는 추정이 근거 없는 정밀도를 흉내 내는 것에 불과하다 — 이슈 본문이 예고한 "비용
추정치만 낸다"는 조건은, OFF 쪽에 더 가까운 오더(§4의 OFF 행, 상한으로 mori 행)로 유보 범위를
제시하는 것으로 대신한다: **OFF 행 이상, mori 행 이하로 추정**하되, 정확한 arm 구현 없이는
이 범위조차 확정할 수 없다.

### 4-c. OFF 팔 — 압축 1회분 asymmetry (분리 표시)

**OFF와 mori/oracle은 세션당 호출 수가 다르다.** `runner.ts:390-398`이 원인이다 —

```
if (options.condition === "memory-off") {
  const compaction = await contextResult.session.compact();
  options.costLedger.record(BENCH_AXES.cost, compaction.usage);
  ...
}
```

세 팔 모두 같은 맥락 세션을 돌리지만(`runner.ts:337` 주석 — 비용 축을 팔 사이에 비교
가능하게 하려는 설계), **OFF만 세션 종료 직전에 `session.compact()` 호출 1건이 추가된다.**
mori(`memory-on`)·oracle 팔에는 이 호출이 없다. 2026-08-10 owner 코멘트가 이것을 "버그가
아니라 그 팔의 진짜 비용"으로 확정했다 — mori 없이 맥락을 이월하려면 실제로 그 압축을
치러야 한다.

이 압축 호출의 **정확한 토큰/비용을 원장에서 단독으로 분리할 수 없다** — `cost-ledger.ts`는
`record(axis, usage)`를 호출별이 아니라 axis 단위로만 누적하므로, "cost" axis 안에서
맥락 턴·압축·후속 턴을 구분하는 필드가 없다. 대신 압축 호출의 **성격**으로 근사한다: 압축은
mori 증류와 같은 크기의 입력(누적 맥락 전체)을 읽지만, 출력은 짧은 구조화 요약이다(실측
`compactionSummary` 표본이 문단 몇 개 수준 — §3의 15% 증류-출력 가정보다 훨씬 작다). 따라서
OFF 팔의 단가를 "입력만 과금되고 출력은 무시할 만하다"는 근사로 잡으면:

```
OFF 근사 단가 = 블렌디드 단가 × (input 단가 ÷ 블렌디드 단가)
             = 블렌디드 단가 × (0.14 ÷ 0.182)   [DeepSeek 실측 비율]
             ≈ 블렌디드 단가 × 0.769
```

이 0.769 배율은 **DeepSeek에서만 실측된 input:output 단가 비로 역산한 것**이고, 다른
두 티어에는 실측 없이 같은 비율을 그대로 전이했다 — 표의 OFF 행에 `~`를 붙인 이유다.
상한은 mori 행과 같다(압축 출력이 실제로는 15%보다 작으므로, mori 행보다 낮은 것은 확실하되
얼마나 낮은지는 티어별 실측이 없으면 확정할 수 없다).

## 5. 측정 한계 — 재산정 사용 시 반드시 반영

### 5-a. mori 팔의 세션종료 consolidation 비용이 원장에 아예 잡히지 않는다 (신규 발견, 하방 편향)

`session.ts:111`의 `close(): Promise<void>` — 세션 종료가 반환하는 것은 `void`뿐이다.
`memory-on` 팔에서 `close()`는 내부적으로 `consolidateOnSessionEnd(kernel, sessionEndLlm(llm,
projectId), stderr)`를 호출하고(`session.ts:245-260`), 이 함수는 `llm`이 설정돼 있으면
`consolidateGuarded`로 **실제 LLM 호출을 낸다**(`cli/consolidation.ts:75-86`). 그런데
`close()`의 반환 타입에 `usage`가 없으므로 **이 호출을 어떤 caller도 원장에 기록할 방법이
없다** — `runner.ts`가 명시적으로 `record`하는 지점은 맥락 턴(`:387`)·압축(`:396`)·후속
턴(`:427`) 셋뿐이고, close()의 consolidation은 그 목록에 없다(있을 수가 없다, API가 값을
안 준다).

**이것이 뜻하는 것: #401의 원장 $0.0170·§2에서 역산한 단가는 mori 팔(memory-on)의 진짜
ingestion 비용 — 증류 자체의 LLM 호출 — 을 포함하지 않는다.** §4-a의 mori 행은 InMind
견적(별도 증류 패스를 명시적으로 모델링한 수치)을 썼기 때문에 이 누락의 영향을 받지 않지만,
**§2의 실측 단가($0.14/M 입력, $0.28/M 출력)는 mori 팔의 실제 증류 비용을 검증하는 데 못
쓴다** — 그 단가는 맥락 턴·압축·후속 턴(모두 close() 밖에서 명시적으로 기록되는 호출)에서만
나온 값이지, mori 팔에 고유한 증류 자체는 섞여 있지 않다.

방향은 **과소추정(하방 편향)**이다 — §5-b(캐시 미스로 인한 상방 편향)와 반대 방향이라
순 방향은 이 재산정만으로 특정할 수 없다.

### 5-b. #445 미해소 — 캐시 재현성 결함(상방 편향 가능)

[#401 run 문서](preference-regression-3arm-run-2026-08-14.md) §4·§5가 이미 규명했다: 캐시
키에 회차 인덱스가 없는데도 동일 명령 재실행이 계속 새 호출을 친다. 이 결함이 이 문서
작성 시점(2026-08-14) 기준 **미해소** 상태이므로, 이번 회차의 원장 수치에는 "캐시가
잡았어야 하는데 못 잡은 중복 호출"이 섞여 있을 수 있다. (원인은 `workRoot`의 `mkdtemp`가
아니라 `Context.messages[].timestamp`가 캐시 키에 섞여 들어가는 것으로 특정됐고, 수정이
[PR #447](https://github.com/shakystar/mori/pull/447)로 리뷰 대기 중이다 — 머지되면 이
문단은 더 이상 유효하지 않다.)

**다만 §2에서 실제로 쓴 것은 원장 "총액"이 아니라 "단가"(`cost ÷ tokens`)다.** 중복 호출은
분자(cost)·분모(tokens)를 같은 비율로 늘리므로 단가 자체는 #445의 영향을 받지 않는다 —
**이 재산정의 §2·§3·§4 수치는 #445로부터 안전하다.** #445가 위협하는 것은 "이번 회차가
실제로 얼마를 썼는가"(잔액 실측 쪽 질문)이지, "토큰당 얼마인가"(이 재산정이 쓰는 질문)가
아니다. 그래도 전제로 남겨둔다 — 원장 데이터의 다른 용도(예: 회차별 비교)에는 여전히
영향을 준다.

### 5-c. OFF 행 배율(0.769)의 티어 간 전이는 미검증

§4-c에서 밝혔듯, DeepSeek에서만 실측된 input:output 단가 비를 GPT-5.6 Luna·Claude Sonnet
4.6에 그대로 전이했다 — 두 티어의 실제 input:output 가격 비가 DeepSeek과 다르면 OFF 행의
추정치는 그만큼 어긋난다.

### 5-d. 공식 memory tool 행은 추정치가 아니라 유보

§4-b 참고 — 구조적으로 다른 비용 모델을 가질 가능성이 높아 숫자를 내지 않았다. #344가
그 arm을 실제로 구현한 뒤 재산정이 필요하다.
