# PreferenceRegression 3팔 실측 — `--repeats 3` 두 회차 (#469, #457 조각 1/2) — 2026-08-15

## 판정

**계기(計器) 자체를 고친 뒤의 첫 반복 실측이다.** [#460 회차](preference-regression-3arm-run-2026-08-15-post-wiring.md)가
`--repeats 1`의 단일 표본 위에서 3/3 킬 스위치 발동으로 아무것도 판정하지 못한 뒤, #469가
그 원인 중 「반복해도 표본이 늘지 않는다」를 고쳤다 — 캐시 키에 회차 인덱스가 들어가 같은
(시나리오, 팔, 프롬프트)라도 회차가 다르면 다른 엔트리가 된다.

같은 명령(`--repeats 3`, 시나리오 3건 × 팔 3개 = 27 에피소드)을 **같은 캐시 디렉터리에
연달아 두 번** 돌렸다. 두 번째는 원래 재생(#342 완료 조건 2)을 확인하려던 실행인데, §4가
적는 이유로 재생이 되지 않고 **독립된 두 번째 표본**이 됐다 — 그래서 이 리포트는 n=3 회차
둘을 나란히 싣는다. 모델은 세 자리(`MORI_MODEL`·`MORI_CONSOLIDATE_MODEL`·judge) 모두
`deepseek/deepseek-v4-flash`, 비용은 1회차 $0.1174 + 2회차 $0.0972.

**결과 1 — 반복이 실제로 독립 표본이 됐다(완료 조건 1).** 두 회차 각각에서, 9개
(시나리오, 팔) 조합 **전부**의 회차 3건이 서로 다른 후속 응답을 냈다(9/9, 두 회차 모두).
점수도 갈렸다 — 1회차는 9개 조합 중 5개, 2회차는 8개가 표준편차 > 0이다. #459 §4가 지적한
「반복이 1회차의 복제를 낳는다」는 더 이상 관측되지 않는다.

**결과 2 — n=3은 아직 판정을 세우기에 부족하고, 이제 그 사실이 리포트에서 보인다.**
`tabs-indentation`은 1회차에서 ORACLE−OFF = **+0.500**으로 킬 스위치를 통과했는데(그 회차
세 팔 모두 sd=0), 2회차에서는 같은 시나리오가 **+0.167**로 발동했다. 두 회차를 합치면
(n=6) gap은 +0.333이다. 즉 이 시나리오에는 신호가 있을 가능성이 높지만 **n=3 하나로는
통과/발동이 뒤집힌다.** 나머지 두 시나리오는 두 회차 모두 발동했고 합쳐도 gap 0.000이다.

이 「뒤집힘을 볼 수 있다」가 이번 조각의 산출물이다. #460 회차에서는 점수 하나만 표에
있어 gap 0.00이 «잴 수 없는 시나리오»인지 «표본이 하나뿐»인지 구분할 방법이 없었다. 이제
표에 n과 산포가 함께 있어, 두 시나리오의 sd(0.19~0.47)가 gap(0.167)보다 크다는 것이
바로 읽힌다 — 그것이 판정이 아직 못 서는 이유다.

**여전히 유보:** 팔 간 델타(합산 OFF 0.722 vs ON 0.500 vs ORACLE 0.833)는 이 표본으로
판정하지 않는다. 시나리오 대부분이 무효 판정을 받은 회차의 델타는 부호를 읽을 근거가
되지 못한다(#401·#460과 같은 판단). ON 팔의 주입 자체는 두 회차 모두 안정적이다 —
`injectionHitRate` 1.000(9/9), 무주입 폴백 발동 0건.

| ------------------- | ---- | ------- | -------- | ------- | ----------- | ---------- | -------------- |
| `tabs-indentation`  | 1    | 3       | 0.500    | 0.500   | 1.000       | **+0.500** | 통과           |
| `tabs-indentation`  | 2    | 3       | 0.667    | 0.333   | 0.833       | +0.167     | 발동(gap<0.25) |

| `concise-responses` | 1    | 3       | 0.833    | 0.333   | 0.667       | −0.167     | 발동           |

¹ **킬 스위치 판정은 이 표의 «평균» 위에서 이뤄진다** — 회차별 점수 하나가 아니라 팔당 n회의
산술평균이다. 킬 스위치(`kill-switch.ts`)와 이 표의 평균은 `sample-stats.ts`의 **같은 추출·요약
함수**를 쓴다. 회차 하나의 우연한 저점으로 시나리오 전체가 무효 판정되지 않게 하기 위한 것이고,
그 평균이 딛고 선 표본은 §2에 그대로 있다. 「합산」 행은 CLI가 판정한 값이 아니라 두 리포트를
사후에 합친 참고값이다(한 실행의 산출물이 아니므로 킬 스위치 열을 비웠다).

## 2. 팔별 표본 산포

각 회차 JSON 리포트의 `sampleStats`를 그대로 옮긴 것이다. `sd`는 **모집단** 표준편차(n으로
나눔) — n=1에서 `NaN`이 아니라 0이 나오게 하기 위한 선택이고, 근거는 `sample-stats.ts`의
`ScoreSummary.stdDev` 주석에 있다.

| 시나리오            | 팔     | 1회차 n·평균·sd·[min,max]   | 2회차 n·평균·sd·[min,max]  |
| ------------------- | ------ | --------------------------- | -------------------------- |
| `tabs-indentation`  | OFF    | 3 · 0.500 · 0.000 · [.5,.5] | 3 · 0.667 · 0.236 · [.5,1] |
| `tabs-indentation`  | ON     | 3 · 0.500 · 0.000 · [.5,.5] | 3 · 0.333 · 0.236 · [0,.5] |
| `tabs-indentation`  | ORACLE | 3 · 1.000 · 0.000 · [1,1]   | 3 · 0.833 · 0.236 · [.5,1] |
| `concise-responses` | OFF    | 3 · 0.833 · 0.236 · [.5,1]  | 3 · 0.500 · 0.408 · [0,1]  |
| `concise-responses` | ON     | 3 · 0.333 · 0.471 · [0,1]   | 3 · 0.333 · 0.236 · [0,.5] |
| `concise-responses` | ORACLE | 3 · 0.667 · 0.236 · [.5,1]  | 3 · 0.667 · 0.236 · [.5,1] |
| `pnpm-workflow`     | OFF    | 3 · 0.833 · 0.236 · [.5,1]  | 3 · 1.000 · 0.000 · [1,1]  |
| `pnpm-workflow`     | ON     | 3 · 0.833 · 0.236 · [.5,1]  | 3 · 0.667 · 0.471 · [0,1]  |
| `pnpm-workflow`     | ORACLE | 3 · 1.000 · 0.000 · [1,1]   | 3 · 0.833 · 0.236 · [.5,1] |

읽는 법: 1회차 `tabs-indentation`은 세 팔 모두 sd=0(세 번 돌려 세 번 같은 점수)이라 그
회차 안에서는 gap 0.500이 흔들림 없는 값처럼 보인다. 2회차에서 같은 세 팔의 sd가 전부
0.236으로 올라가고 gap이 0.167로 떨어졌다 — **회차 내 산포가 0이어도 회차 간 재현은 별개
문제**라는 것이 이 표 두 개를 나란히 놓았을 때 나오는 결론이다. 표본을 더 키우는 것(§6)
외에 지름길이 없다.

## 3. 회차가 실제로 독립 표본인가 (완료 조건 1)

27개 레코드는 각각 `repeatIndex`(0·1·2)를 달고 있다. 각 (시나리오, 팔) 조합의 회차 3건이
서로 다른 `followUpOutput`을 냈는지 세면 두 회차 모두 **9/9**다. 1회차 상세:

```
tabs-indentation |memory-off  reps=0,1,2  서로 다른 응답 3/3  scores=0.5,0.5,0.5
tabs-indentation |memory-on   reps=0,1,2  서로 다른 응답 3/3  scores=0.5,0.5,0.5
tabs-indentation |oracle      reps=0,1,2  서로 다른 응답 3/3  scores=1,1,1
concise-responses|memory-off  reps=0,1,2  서로 다른 응답 3/3  scores=1,1,0.5
concise-responses|memory-on   reps=0,1,2  서로 다른 응답 3/3  scores=1,0,0
concise-responses|oracle      reps=0,1,2  서로 다른 응답 3/3  scores=1,0.5,0.5
pnpm-workflow    |memory-off  reps=0,1,2  서로 다른 응답 3/3  scores=1,0.5,1
pnpm-workflow    |memory-on   reps=0,1,2  서로 다른 응답 3/3  scores=1,0.5,1
pnpm-workflow    |oracle      reps=0,1,2  서로 다른 응답 3/3  scores=1,1,1
```

`tabs-indentation`처럼 응답이 셋 다 다른데 점수는 같은 조합이 있다는 것도 그 자체로
정보다 — 그 시나리오의 루브릭은 응답 표면이 흔들려도 같은 판정을 낸다(그래서 그 회차의
sd=0).

## 4. 재생(replay) 관측 — «같은 명령 재실행 = API 호출 0건»은 이 층에서 성립하지 않는다

완료 조건 2를 검증하다 발견한 사실이며, **이번 변경이 만든 것이 아니라 원래 그랬다.**

- **캐시 계층 자체의 재생 보장은 유지된다.** `withLlmCallCache`는 같은 회차 인덱스를 같은
  순서로 다시 밟으면 그대로 재생한다 — 기존 테스트 `nightly-slice.test.ts`의
  「reruns against the same cacheDir for free — second call makes zero streamFn calls (#422)」
  (스텁 세션, 실호출 **0건**)가 이 변경 후에도 그린이고, `llm-call-cache.test.ts`의 재생
  테스트도 그대로다. 새로 넣은 테스트가 같은 자리에서 「인덱스가 다르면 실호출, 같으면
  재생」을 함께 못박는다.
- **그런데 실제 `bench:nightly-slice` 명령은 재실행해도 0건이 되지 않는다.** 이 층은
  에피소드 세션 턴에 `cacheStore`를 아예 넘기지 않기 때문이다
  (`preference-regression/runner.ts`의 `RunEpisodeOptions.cacheStore` 주석 — #423에서
  의도적으로 비범위였다). 캐시를 타는 것은 judge/reader 호출뿐이고, 에피소드가 매번
  실호출이라 그 출력이 달라지면 judge 프롬프트까지 달라져 judge도 대부분 미스가 된다.
  증류(consolidation) 호출은 `getConsolidatorLlm`(cli/runtime.ts)이 `models`에서 직접
  만들어 이 `streamFn`도 캐시도 타지 않는다.
- **관측치** (이번에 CLI에 추가한 `provider 스트림 호출` 카운터 — 캐시 적중은 세지 않는다):

  | 실행                                        | provider 스트림 호출 | 총비용  |
  | ------------------------------------------- | -------------------- | ------- |
  | 1회차 (빈 캐시 디렉터리)                    | 481건                | $0.1174 |
  | 2회차 (같은 명령·같은 캐시 디렉터리 재실행) | 399건                | $0.0972 |

  줄어든 82건이 캐시가 실제로 먹은 부분(회차 인덱스까지 같고 프롬프트도 같았던 judge 호출)
  이다. 「0건」과는 거리가 멀다.

`nightly-slice-cli.ts`의 #422 주석("Reusing the cache dir is what makes a rerun ... free
instead of full price")은 이 점에서 낙관적이다. 이 리포트는 그 사실을 **기록만 하고 고치지
않는다** — 에피소드를 캐시에 태우는 것은 「실비용 API 경로」라는 이 층의 존재 이유
(`nightly-slice.ts`의 `runNightlySlice` 문서: 캐시 재사용이 이 층을 PR 스모크 층과
구별할 수 없게 만든다)와 정면으로 부딪치므로, 방향 결정이 필요한 사안이다.

## 5. 캐시 무효화 조건 (#469 요구 1의 설계 판단)

회차 인덱스는 (모델, 프롬프트, 파라미터) 옆의 **별도 최상위 계층**으로 들어간다 — 생성
파라미터가 아니기 때문이다. 모델에게 던지는 질문은 회차마다 동일하고, 인덱스는 «이 질문을
다시 뽑는다»는 러너 쪽 선언이다.

무효화가 일어나는 조건은 하나다: **회차 인덱스를 선언하는 호출자의 기존 캐시 엔트리.**
구체적으로 `bench:nightly-slice`의 judge/재질문 reader 호출이고, 이 경로의 캐시 디렉터리는
이 변경 이후 첫 실행에서 한 번 다시 채워진다. 인덱스를 선언하지 않는 호출자
(`milestone.ts`, PR 스모크의 judge)의 키는 바이트 단위로 종전과 같아 그 엔트리는 그대로
유효하다.

회차 0을 «인덱스 없음»과 같은 키로 접는 선택지도 있었고, 그러면 무효화 자체가 없어진다.
택하지 않은 이유: 그러면 반복 N회 중 **0회차 하나만** 예전 실행·다른 경로의 캐시 슬롯을
공유하게 되어, 표본 하나가 나머지 N−1과 다른 조건에서 뽑힌 값이 된다. 표본의 균질성이
캐시를 한 번 다시 채우는 비용보다 비싸다.

## 6. 다음 (이 회차 범위 밖)

- **표본을 더 올린다** — §2가 보여주듯 n=3은 회차 간 재현이 안 된다. 기본값
  `DEFAULT_SLICE_REPEATS_PER_SCENARIO`는 이미 10이므로, 다음 실측은 `--repeats`를 빼고
  기본값으로 돌리는 것이 자연스럽다(비용은 이 회차의 3배 남짓).
- **임계값(0.25) 재조정** — 표본이 커진 뒤에 판단한다. #469 비범위였다.
- **에피소드 캐시 정책** — §4. 재실행 비용을 0으로 만들지, 실비용 신호를 지킬지의 선택.
- **주입물 감사** — #457 조각 2/2. 도메인 어휘 중립화·비개발 시나리오 추가는 그 뒤다.
