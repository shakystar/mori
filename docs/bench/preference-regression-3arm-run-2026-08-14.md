# PreferenceRegression 3팔 실측 (#401, #343 조각 3/4) — 2026-08-14

## 판정

**실행은 됐고, 수치는 무효다.** 재정의된 3팔(OFF=하네스 압축 요약 / ON=mori 증류물+retrieval /
ORACLE=`impliedPreference` 직접 주입)을 DeepSeek `deepseek-v4-flash`로 실제 호출해 끝까지
돌렸다. 그러나 **킬 스위치(#435)가 발동한다** — `concise-responses`에서 ORACLE−OFF 간격이
0이라, 그 시나리오는 "기억이 있으면 풀리고 없으면 못 푸는 문제"가 아님이 실측으로 드러났다.
킬 스위치의 설계 의도대로 이 리포트는 스스로 무효를 낸다.

무효 판정과 별개로, 나온 수치의 방향 자체가 mori 명제와 반대다: **ON(0.167)이 OFF(0.333)보다
낮다.** 주입 적중률도 3건 중 1건(33.3%)이다. 이 두 가지는 킬 스위치가 걸리지 않은
나머지 두 시나리오에서도 그대로 나타나므로, "무효라서 아직 모른다"가 아니라
"현재 배선으로는 mori 팔이 이득을 못 낸다"가 이번 실측이 말하는 것이다.

추가로, 이 이슈 본문의 **게이트 조건 1("재현 실행은 API 호출 0건")이 성립하지 않는다** —
아래 §4.

## 1. 팔별 점수

`--repeats 1`, 시나리오 3건 × 팔 3개 = 9 에피소드. 점수는 시나리오당 기준 2개(결정론 1 +
LLM 심판 1)의 충족 비율이다.

| 시나리오            | OFF   | ON    | ORACLE | ORACLE−OFF | 킬 스위치      |
| ------------------- | ----- | ----- | ------ | ---------- | -------------- |
| `tabs-indentation`  | 0.0   | 0.0   | 1.0    | 1.00       | 통과           |
| `concise-responses` | 0.5   | 0.0   | 0.5    | **0.00**   | **발동(무효)** |
| `pnpm-workflow`     | 0.5   | 0.5   | 1.0    | 0.50       | 통과           |
| **평균**            | 0.333 | 0.167 | 0.833  | 0.50       | 임계값 0.25    |

**행동 적응 델타 (ON−OFF) = −0.167.** 부호가 음수다 — mori 증류물+retrieval을 받은 팔이
하네스 기본 압축 요약만 받은 팔보다 낮았다. `tabs-indentation`에서 ON은 OFF와 같이 0점이고,
`concise-responses`에서는 ON만 0점으로 OFF보다 낮다.

ORACLE−OFF = 0.50은 "천장은 존재한다"는 뜻이다 — 즉 정답 선호를 컨텍스트에 직접 넣어주면
모델이 그 선호를 실제로 따른다. 문제는 mori 경로가 그 정보를 후속 세션까지 못 옮기고 있다는
쪽이지, 과제가 원천적으로 불가능한 쪽이 아니다 (`concise-responses` 제외 — 거기선 천장 자체가 없다).

## 2. 계기판 (주입 적중률 포함)

| 지표                             | 값        | 비고                                                        |
| -------------------------------- | --------- | ----------------------------------------------------------- |
| `injectionHitRate` (주입 적중률) | **0.333** | ON 팔 3건 중 `pnpm-workflow` 1건에서만 retrieval이 주입됐다 |
| `reQuestionRate` (재질문율)      | 0.000     | ON 팔이 이미 확립된 습관을 되묻지는 않았다                  |
| `reDistillationRate` (재증류율)  | 0.000     | 이번 슬라이스에서 측정 경로 미사용                          |

주입 적중률 33.3%가 §1의 음수 델타를 설명한다: ON 팔 3건 중 2건은 **retrieval이 아무것도
주입하지 못했다**. 아무것도 주입되지 않은 ON 팔은 "압축 요약조차 없는 맨 세션"이 되므로,
하네스 압축 요약을 받는 OFF 팔보다 오히려 불리하다. 즉 현재 배선에서 ON은 OFF의 상위집합이
아니라, 주입이 실패하면 OFF보다 **적게** 받는 팔이다. 이것이 팔 정의(#434)의 의도인지
회귀인지는 이 이슈 범위 밖이라 판단하지 않는다 — 후속에서 볼 것.

## 3. 실측 usage / 비용

| 항목                     | 값                                               |
| ------------------------ | ------------------------------------------------ |
| 모델                     | `deepseek/deepseek-v4-flash`                     |
| 원장(ledger) 집계 비용   | $0.0170                                          |
| 원장 집계 토큰           | input 56,668 / output 25,689 / cacheRead 656,768 |
| **프로바이더 잔액 실측** | 실행 전후 통틀어 $10.00 → **$9.48** (= $0.52)    |

**사전 승인 범위(회당 ~$20–40, ablation 포함 ~$100 미만) 안이다** — 실지출은 두 자릿수 센트
수준으로, 승인 상한의 1% 미만이다. 하드캡(DeepSeek 선불 잔액 $10)은 건드리지 않았다.
$0.52는 이 세션의 실행뿐 아니라 직전 세션(2026-08-14 17:05–17:24)이 캐시를 데운 몫까지 포함한
누적치다.

**원장 수치를 실지출로 읽으면 안 된다.** `cost-ledger`는 캐시 replay된 호출도 저장된
`usage`(원래 호출의 비용)를 그대로 계상한다 — `llm-call-cache.ts`가 캐시 파일에 응답의
`usage.cost`를 통째로 저장하고, replay 시 그 메시지를 그대로 흘리기 때문이다. 위 표의
cacheRead 656,768 토큰이 그 증거다. 따라서 원장의 $0.0170은 "이 호출들을 캐시 없이 다 쳤다면
들었을 비용"(모델링된 비용)이지 이번에 실제로 나간 돈이 아니다. 실지출 판정은 잔액 실측으로만
해야 한다. (코드 레벨 지출 상한 가드는 사람 결정 3항에 따라 #402 소관이라 여기서 고치지 않았다.)

## 4. 게이트 조건 1 위반 — 재현 실행이 API 호출 0건이 아니다

이슈 본문은 "캐시 경유로 실행 — 재현 실행은 API 호출 0건"을 게이트로 걸고 있다.
**성립하지 않는다.** 같은 명령(`bench:nightly-slice --repeats 1`)을 연속으로 두 번 돌리면
두 번째도 새 프로바이더 호출을 친다.

증거 (`/data/bench-cache` 신규 파일 수 = 캐시 미스 수):

| 실행                                        | 시각 (UTC)  | 신규 캐시 파일                             |
| ------------------------------------------- | ----------- | ------------------------------------------ |
| 직전 세션이 데운 캐시                       | 17:05–17:24 | 220 (누적)                                 |
| `--repeats 1` 1회차                         | 17:54–18:02 | +21                                        |
| `--repeats 1` 2회차 (**1회차와 완전 동일**) | 18:09–18:11 | +8 (580초 타임아웃으로 중단, 계속 증가 중) |

팔을 좁혀서 재확인해도 같다 — mori 스토어를 아예 만들지 않는 `memory-off` 팔만
같은 시나리오로 두 번 돌려도 매 회차 +1건씩 새로 미스가 난다. 즉 이것은 mori 커널
쪽(회차마다 새 `memorizeRoot`를 쓰는 설계) 만의 문제가 아니라 **store-free 팔에서도 나는
미스**다.

캐시 키는 `(모델 identity, 전체 Context, 생성 파라미터)`이고 회차 인덱스나 논스는 들어가지
않으므로(`llm-call-cache.ts:llmCallCacheKey`), 미스가 난다는 것은 **회차마다 Context가
실제로 달라진다**는 뜻이다. 무엇이 달라지는지까지는 이번 세션에서 특정하지 못했다 —
`workRoot`/`memorizeRoot`가 회차마다 새 `mkdtemp`인 것이 유력한 후보지만(#423 함정 방지
주석이 요구하는 바로 그 성질이다), 확증하려면 회차 간 Context diff가 필요하고 그 계측을
붙이려던 시도는 하네스 compaction 경로를 건드려 실패했다. **원인 특정은 후속 이슈 몫으로
남긴다.**

이것이 중요한 이유는 비용이 아니라 **의미**다. 재현이 공짜가 아니면 나이틀리·마일스톤
케이든스(#397)가 매 실행 full price로 돌고, 사람 결정(2026-08-09)이 키를 열기 전에 세우려던
전제("실수로 두 번 돌리면 두 배 나간다"의 차단)가 절반만 선다. `#422`·`#423`이 고친 것은
캐시 디렉터리의 **영속화**이지 캐시의 **적중**이 아니었다.

## 5. 반복(`--repeats N`)에 대한 주의

캐시 키에 회차가 안 들어가므로, 캐시가 데워진 뒤의 반복은 **원리상 같은 응답을 replay**한다.
그런 회차들은 서로 독립 표본이 아니라 같은 표본의 복제이고, 평균을 내도 분산이 줄지 않는다.
브랜치의 `fix(bench): 킬 스위치 판정이 반복 실행의 첫 회차만 보던 것을 평균으로 고친다`
커밋은 여전히 옳다(캐시가 차갑거나 미스가 나는 회차에서는 실제로 값이 갈린다) — 다만
**"repeats를 올리면 통계적 신뢰도가 올라간다"고 읽으면 안 된다**는 단서를 여기 남긴다.

이번에 `--repeats 10`(기본값)을 돌리지 않은 것도 같은 이유다: §4 때문에 반복이 공짜가
아니고(회차마다 실호출이 늘고), §5 때문에 반복이 표본을 늘려주지도 않으며, 무엇보다
킬 스위치가 이미 발동해 **N을 키워도 리포트는 여전히 무효**다. 잔액이 하드캡인 상황에서
무효 리포트의 N을 키우는 데 상한을 쓰는 것은 사람 결정(2026-08-09)이 막으려던 지출 그 자체라
판단했다.

## 6. 다음에 해야 할 것 (이 이슈 범위 밖)

1. **`concise-responses` 시나리오 재설계 또는 제외** — ORACLE−OFF = 0이라 기억 유무를
   판별하지 못한다. 기준 `short-response`(200자 이하)가 ORACLE에서도 불충족인 것이 원인으로
   보인다(천장 자체가 0.5에 막혀 있다).
2. **주입 적중률 33.3%의 원인 규명** — ON 팔 3건 중 2건에서 retrieval이 아무것도 주입하지
   못한 것이 §1 음수 델타의 직접 원인이다.
3. **재현 캐시 미스의 원인 특정** (§4) — 게이트 조건 1을 실제로 세우는 일.
4. **원장의 replay 계상 분리** (§3) — 모델링 비용과 실지출을 같은 필드로 내보내지 않기.
   사람 결정 3항에 따라 #402와 묶인다.
